# Настройки участка — версия 0.7

Форма: `http://127.0.0.1:4173/#settings`. Сервер — 0.7.0, интерфейс — 0.11.0. Для настройки участка нужен запущенный API 0.7.0: перезапустите старый сервер через `start.cmd` и обновите страницу. Это обновление не меняет структуру SQLite.

## Что задаётся

| Поле | Диапазон | Учебное значение |
|---|---|---|
| План годного выпуска | Целое 1–100000 | 410 |
| Интервал подачи, с | Целое 5–3600 | 65 |
| Нормативные циклы P01–P05, с | Пять целых 5–3600 | 48, 52, 58, 50, 55 |
| Вместимости B01–B04 | Четыре целых 1–100 | 6, 6, 6, 6 |

Топология, названия постов, длительность смены 08:00–16:00 и правило брака (каждое 25-е изделие) остаются заданными для MVP. Нельзя убрать пост или создать параллельную ветвь этой формой. Указанные пределы — диапазон демонстрационной модели, не подтверждённые нормативы завода.

## Как применяется конфигурация

1. Форма загружает параметры текущего сценария. Последующий опрос сервера не затирает черновик.
2. Ввод проверяется до отправки и повторно сервером. Пустые, дробные, отрицательные значения, неверное число элементов и лишние поля отклоняются.
3. «Применить и начать сценарий» явно создаёт новый runId. Модель пересчитывает первые 45 минут с новыми значениями и останавливается в 08:45, скорость 20×. У всех постов нормальный режим; старые остановки в новый запуск не переносятся.
4. Предыдущий сценарий остаётся в `runs` со своими параметрами, выпуском и событиями. Настройки представлены прямо в состоянии: `shiftPlan`, `arrivalIntervalSec`, `stations[].nominalCycleSec`, `buffers[].capacity`. Второй несогласованной копии конфигурации нет.
5. Обычный «Сбросить» также создаёт новый runId, сохраняя параметры текущего сценария. Для исходного демонстрационного набора нажмите «Базовые параметры», затем примените форму.
6. Если runId изменился во время редактирования, черновик сохраняется, а применение блокируется. «Загрузить актуальные параметры» или «Вернуть текущие» заменяет черновик данными нового сценария.

Сетевой повтор использует прежний commandId и тот же ожидаемый runId. Повтор не создаёт дополнительный запуск, в том числе после перезапуска сервера. При конфликте 409 клиент не переносит команду на новый сценарий автоматически. Ошибка сохранения не заменяет текущий снимок в памяти и не регистрирует выполненную команду.

## Контракт API

Через `POST /api/v1/commands`, JSON:

```json
{
  "type": "configure_line",
  "commandId": "11111111-1111-4111-8111-111111111111",
  "runId": "22222222-2222-4222-8222-222222222222",
  "configuration": {
    "shiftPlan": 275,
    "arrivalIntervalSec": 80,
    "stationCyclesSec": [45, 60, 95, 40, 65],
    "bufferCapacities": [2, 3, 4, 5]
  }
}
```

Замените runId на текущий, а commandId — на новый UUID для нового действия. Порядок массивов фиксирован: P01–P05 и B01–B04. Ответ 200 — новый `TwinSnapshot`, 422 — неверные параметры, 409 — устаревший runId или повтор commandId с другим содержимым.

Текущий снимок и ответы на команды содержат `capabilities: ["configure_line", "history_configuration"]`. Поле описывает возможности работающего сервера и не является параметром производственного сценария. При отсутствии configure_line форма настроек показывает сообщение о старом сервере и не разрешает отправку. Старые снимки и архив не требуют этого поля.

## Контрольный пример

С конфигурацией из JSON выше в 08:45 модель даёт **25 годных изделий**, прогноз к 16:00 — **288**, отклонение от плана 275 — **+13**, ограничение — **P03** с нормативом 95 с. Это результат условной модели, не измерение производства.

После «Сбросить» эти значения воспроизводятся. После применения учебных параметров снова получаются начальные 37 годных и прогноз 423 при плане 410. Для сценария остановки P03 из презентации сначала восстановите именно учебную конфигурацию.

## Связь с другими разделами

- Мониторинг, прогноз и сравнение восстановления используют параметры состояния выбранного рабочего сценария.
- Архив показывает план, подачу, нормативы и буферы выбранного сохранённого запуска, включая экспорт JSON и печать.
- При вместимости больше 12 мест точки на схеме показывают долю заполнения; точные количества всегда указаны числами. Для буферов до 12 мест одна точка соответствует одному месту.
- CSV-проверка метода `flow-history-v2` позволяет выбрать «Копия текущих настроек» в разделе «История». Копируются применённые параметры; последующие изменения рабочего сценария не обновляют копию автоматически. План импортируемой смены можно изменить отдельно. Каждый новый отчёт хранит свою конфигурацию; ранее сохранённые отчёты не пересчитываются. Подробности — HISTORY_IMPORT.md.

## Проверка перед показом

В отдельном демонстрационном запуске примените контрольный пример, проверьте новые параметры на линии, затем выполните сброс. Откройте предыдущий сценарий в архиве и убедитесь, что его нормативы сохранились. Проверьте пустое поле, 0, дробное число и 101 место в буфере: применение должно блокироваться. В двух вкладках начните редактировать настройки в первой, создайте новый сценарий во второй, затем проверьте предупреждение о сменившемся сценарии в первой. Перед питчем верните учебные параметры.

Автоматические проверки покрывают модель, контракт, хранение, конфликты и повторные запросы. Интерактивное поведение и компоновка формы ещё требуют визуального прогона: браузерный инструмент в текущей среде не инициализируется.
