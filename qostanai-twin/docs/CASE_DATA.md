# Данные кейса и объяснимый анализ

Раздел: http://127.0.0.1:4173/#case. Версия интерфейса 0.11.0. Источник — переданный пользователем файл «Кейс_Цифровой_двойник_Тестовые_данные.docx» с заголовком «Тестовые данные для кейса “Цифровой двойник завода”». Это тестовый набор, а не подтверждённая телеметрия АЛЛЮР.

## Что перенесено

Все четыре таблицы прочитаны из Word: 6 записей работы трёх линий за 1–2 октября 2026, 4 простоя, 3 месячных плана по моделям и 6 записей качества. Также сохранены схема из 6 этапов и пять вводных. Изображений и отслеживаемых исправлений в документе нет. Оригинал не изменялся.

Нормализованный источник — `src/case-dataset.json`. В нём сохранены имя файла, SHA-256 оригинала, исходные округлённые проценты, числа и неизвестные параметры. Даты преобразованы в ISO, десятичная запятая — в числовое значение. Исходный документ не требуется для просмотра готовой сборки и не включён в архив приложения.

Воспроизводимое извлечение из оригинала:

```powershell
.\.venv\Scripts\python.exe -m scripts.extract_case_docx "ПУТЬ-К-ДОКУМЕНТУ.docx" --output src/case-dataset.json
npm.cmd test
npm.cmd run build
```

Экстрактор принимает точные заголовки и вводные текущего документа. При другом формате останавливается для явного сопоставления; инструкции из текста не выполняет. Клиент проверяет диапазоны, даты, дубликаты, согласованность производства/качества и округлённых процентов. Произвольная загрузка новых DOCX через браузер пока не реализована.

## Что работает на сайте

- Выбор даты и участка, схема потока, план/факт, часы и загрузка из файла, таблица качества и сравнение доступных дат.
- Журнал простоев на выбранную дату с исходной причиной и неизвестной критичностью.
- Месячные планы по моделям и сопоставление с общей целью.
- Помощник: «Что проверить первым?», «Сходится ли план?», «Что нужно для ИИ?». Каждый вывод содержит расчёт, источник и действие для проверки.
- Экспорт JSON с исходными данными, выбранной датой, результатами и ограничениями.
- Работа со старым API и доступ к загруженному разделу при недоступности модели: данные включены в сборку. Для открытия страницы сервер статических файлов всё равно нужен.

## Проверяемые выводы

На 2 октября окраска: 6 / 116 × 100 = 5,17% брака, превышение лимита 2% — 3,17 п.п. На сварке 3 / 111 × 100 = 2,70%. На сборке 2 / 119 × 100 = 1,68%, лимит не превышен. За 1 октября лимит превышен только на окраске: 4 / 115 × 100 = 3,48%.

Планы по моделям: 2500 + 1800 + 500 = 4800. Общая цель — не менее 5500 автомобилей в месяц; разница 700. Месяц не указан. Это расхождение исходных планов, а не оценка фактического месячного недовыпуска.

В журнале Конвейер-03: 55 минут 2 октября. Лимит 60 минут в сутки относится только к критическому оборудованию, но его перечня нет. Помощник показывает условный запас 5 минут и предлагает уточнить критичность. Вспомогательный порог внимания 90% лимита введён интерфейсом и явно подписан; он не является правилом источника или вероятностью отказа.

## Что нельзя выводить из этого набора

**Выпуск завода.** Итоги сварки, окраски и сборки не суммируются: это последовательные этапы. На карточке показан выпуск сборки, без утверждения, что все эти изделия прошли конечный контроль качества.

**OEE.** Загрузка и выполнение плана не подставляются вместо OEE. Нет нормативного цикла, планового производственного времени, согласованной границы измерения. Завод работает 2 × 8 часов, но записи 7,2–8 часов не имеют номера смены. Автоматически считать их суточной доступностью или делить на 8 часов нельзя.

**Прогноз простоя и обучение ML.** Две даты, шесть итогов работы и четыре события без времён не дают оснований подтвердить предсказательную точность. Текущий помощник использует правила, модель не обучалась. `forecast` и `oee` в отчёте равны null. Нужны временная история датчиков и событий, критичность, режимы, обслуживание, нормативы, метки отказов, а затем проверка на отдельном более позднем периоде и сравнение с базовым прогнозом.

**Причинность.** Ошибка датчика, фильтр и обрыв цепи сохранены как причины из журнала; они не объявляются причинами брака или снижения выпуска. Нужна привязка ко времени и партиям. Отсутствие записей о простоях не равно нулевому простою. Нет данных о длительности перекрывающихся событий.

**Подмена симулятора.** Нормативы пяти учебных постов и четыре буфера не выводятся из итогов по датам. Учебный сценарий, его история и текущая база сохранены. В документе нет минутных рядов для существующего импорта CSV, поэтому такие ряды не генерировались как фактические измерения.

## Ручная проверка

1. Открыть «Данные кейса»: дата 02.10.2026, сборка 119/120, два участка выше лимита брака, план 4800/5500, OEE без расчёта.
2. Выбрать 01.10.2026: сборка 121/120, один участок выше лимита, две записи простоев. Будущая дата не участвует в изменениях показателей.
3. Нажать «Сварка» на схеме и выбрать «Сборка» в списке: подробности и график переключаются. Склады и ОТК показывают отсутствие измерений.
4. Открыть три вопроса помощника. Проверить условную формулировку лимита и описание необходимых данных для ИИ.
5. Скачать JSON и проверить выбранную дату, исходные округления, null для прогноза/OEE. Перейти в «Обзор» и обратно: учебная линия не сбрасывается.

На коротком показе: «Мы получили тестовые данные кейса. Помощник выделил брак на окраске и расхождение планов, показал формулы и указал, каких данных не хватает для прогноза. Это проверяемая аналитика на текущем наборе; обучение прогноза — следующий этап после накопления истории».
