# HTTP-контракт 0.7

Интерфейс 0.9 добавляет пошаговый показ через существующие reset/configure_line, set_station_mode, advance и analysis/compare. Шаги используют обычный протокол команд; сценарий показа и подсказки хранятся только в браузере. Подробности и проверки состояния — DEMO_GUIDE.md. Новых серверных маршрутов нет.

Интерфейс 0.8 добавляет сравнение сохранённых исторических отчётов через существующие GET /api/v1/history/imports/{importId}. Серверный код и версия API остаются 0.7.0. Сравнение совместимо с чтением отчётов через API 0.4; дополнительных capabilities или серверной записи не требует. Экспорт формируется в браузере. Подробности — HISTORY_COMPARISON.md.

Маршруты остаются `/api/v1/…`, оболочка снимка теперь `schemaVersion: 2`. Внутренняя модель состояния сохраняет `schemaVersion: 1`. Реальный ответ сохранён в `snapshot.example.json`; прежняя модель для проверки порта — `model-v1-reference.json`.

## Чтение

- `GET /api/v1/health` — доступность сервера, хранилище, runId и revision.
- `GET /api/v1/twin` — полный текущий снимок. Чтение не двигает часы.
- `GET /api/v1/runs` — текущий runId и до 50 последних сценариев.
- `GET /api/v1/runs/{runId}` — сохранённый снимок выбранного сценария вместе с событиями и историей выпуска.

Снимок содержит:

| Поле | Смысл |
|---|---|
| schemaVersion | 2 |
| source | simulation; текущая версия использует только модель |
| runId | UUID текущего сценария |
| revision | монотонная версия сохранённого состояния, в том числе после сброса |
| savedAt | UTC ISO 8601 момента сохранения |
| receivedAt | UTC ISO 8601 формирования ответа текущего API; отсутствует в архивном снимке |
| controls | общие `paused` и `speed` (20, 60, 120) |
| state | состояние линии, события и история |
| forecast | последний расчёт прогноза и его модельное время |

Все производственные времена — секунды от начала смены. Реальные UTC-времена не используются в формулах производственного простоя. `remainingWorkSec=null` означает пустой пост, `0` — готовое изделие, ожидающее передачи. Положительное значение убывает со скоростью 1 в нормальном режиме и 0.5 при замедлении.

## Команды

`POST /api/v1/commands`, Content-Type: application/json. Каждая команда содержит уникальный `commandId` и ожидаемый `runId`:

```json
{
  "commandId": "22a46316-541e-4f87-aead-481263b86d11",
  "runId": "75124729-40f9-40e1-aa3b-b120640c1a7e",
  "type": "set_station_mode",
  "stationId": "P03",
  "mode": "stop"
}
```

В примере UUID runId нужно заменить актуальным из GET. Для повтора той же команды после сетевого сбоя сохраняется **тот же commandId и всё содержимое**. Новое намеренное действие получает новый UUID.

| type | Дополнительные поля |
|---|---|
| set_station_mode | stationId: P01…P05; mode: normal / slow / stop |
| acknowledge_incident | incidentId: event-N из текущего снимка |
| advance | seconds: целое 1…3600; используется только для явного шага демонстрации |
| set_playback | paused: boolean и/или speed: 20 / 60 / 120 |
| reset | без дополнительных полей |
| configure_line | configuration: план, интервал подачи, пять циклов и четыре вместимости; создаёт новый сценарий |

Ответ 200 — сохранённый снимок. При повторе commandId возвращается первоначальный результат; браузер не заменяет более новую revision старой. Дедупликация хранится в SQLite и переживает перезапуск.

- 409: commandId уже связан с другими параметрами, runId устарел после сброса другой вкладкой или смена завершена.
- 404: инцидент или архивный сценарий не найден.
- 422: неверные значения, типы или лишние поля.
- 503: сервер не может подтвердить сохранённое состояние.

После 409 клиент получает свежий GET и предлагает повторить действие осознанно. Он не пересоздаёт команду автоматически с другим runId. После сетевой ошибки HTTP-адаптер делает один повтор с прежним commandId.

## Серверные часы и SQLite

Один фоновый цикл запускается в lifespan FastAPI. Он использует monotonic clock и учитывает общую скорость. Запросы из браузеров не запускают собственные часы. При возобновлении процесса время, когда сервер не работал, не догоняется.

SQLite в WAL, `synchronous=FULL`. Снимок, строки инцидентов и истории, указатель активного сценария и результат команды сохраняются одной транзакцией. В памяти состояние заменяется только после успешного commit.

Таблицы: `runs`, `incidents`, `history`, `commands`, `meta`. Ключ события — `(run_id,event_id)`, поэтому event-1 разных демонстраций не конфликтуют. Сброс создаёт новый runId, не удаляя предыдущие записи.

Блокировка файла базы запрещает второй серверный процесс с тем же хранилищем. Запускать Uvicorn с `--workers 1`. Для нескольких независимых демонстраций использовать отдельные базы и серверы.

## Интерфейс

`HttpDataSource` получает снимок раз в секунду. Пауза, скорость и команды — серверные. Ответ проверяется по структуре вложенных данных. Обновления с меньшей revision игнорируются.

При ошибке связи или отсутствии успешного ответа более 5 секунд управление отключается, остаётся последнее известное состояние и предупреждение. Автоматического переключения на вымышленные локальные данные нет.

## Границы версии

Запись разрешена только в демо-модель. Подключение реального оборудования потребует отдельного адаптера чтения, качества и свежести данных, проверки схемы предприятия и прав доступа. Текущий локальный сервер не предназначен для публичной публикации или управления промышленным оборудованием. Встроенной аутентификации нет; обычный запуск привязан к loopback.

## Сравнение сценариев

`POST /api/v1/analysis/compare`, Content-Type: application/json:

```json
{"runId": "b7c79a00-a98f-4e5f-b731-1eaa69f4de2a", "stationId": "P03", "delayMinutes": 30}
```

Подставьте текущий runId. stationId: P01…P05; delayMinutes — строго целое 0…240. Неверный тип, неизвестный пост и лишние поля дают 422; чужой runId — 409. commandId не нужен: этот запрос не записывает состояние, события, историю и команды и не двигает часы.

Сервер делает согласованную копию состояния под блокировкой, затем считает три независимых варианта вне блокировки. Работающая линия продолжает жить своим временем. Ответ относится к `runId`, `baseRevision` и `baseElapsedSec`, а не к состоянию на момент получения ответа.

Ответ имеет собственный `schemaVersion: 1`, исходные параметры, режимы всех постов, допущения и `results` в порядке baseline / restore_now / restore_later. Полный пример — `comparison.example.json`.

| Поле результата | Смысл |
|---|---|
| good / rejected | накопленный выпуск за всю смену к её концу |
| planDelta / planFulfillmentPct | отклонение от плана в изделиях / выполнение плана, % |
| gainVsBaseline | разница годного выпуска с baseline |
| additionalDowntimeSec | будущая длительность остановки выбранного поста; замедление не считается остановкой |
| recoveryAtSec / recoveryWithinShift | момент восстановления до конца смены; null / false для baseline и восстановления вне смены |
| series | начальная точка, каждые 300 модельных секунд, момент восстановления и конец смены |

`summary.maxGain` — максимальная прибавка к baseline среди вариантов; `delayLoss` — разница restore_now и restore_later; `bestScenarioIds` включает все равные лучшие варианты. При завершённой смене каждая кривая содержит единственную фактическую точку.

Интерфейс не применяет рассчитанный вариант автоматически. Отчёт помечается устаревшим после смены runId, выбранного поста, задержки или режимов, а также после продвижения линии на 60 модельных секунд. Экспортирует тот же показанный отчёт с исходными параметрами, включая устаревший, если пользователь решил его сохранить. После перезагрузки страницы расчёт нужно запросить снова; в SQLite он не сохраняется.

## История производства (0.7; чтение отчётов 0.4 сохранено)

- `GET /api/v1/history/example.csv` — синтетический CSV с заголовком скачивания.
- `POST /api/v1/history/import` — JSON `{fileName, csvText, shiftPlan?, configuration?}`; план — целое 1…100000, имя 1…180 символов, CSV до 512 КиБ UTF-8. Configuration имеет тот же строгий контракт, что у configure_line. Без configuration используются учебные нормативы и указанный план (по умолчанию 410). С configuration и без shiftPlan берётся configuration.shiftPlan; если оба плана указаны, они обязаны совпадать, иначе 422. Текущий рабочий сценарий никогда не подставляется автоматически.
- `GET /api/v1/history/imports` — до 20 последних импортов, `{imports: [...]}`.
- `GET /api/v1/history/imports/{importId}` — полный сохранённый отчёт по идентификатору SHA-256.

Ошибки CSV: HTTP 422, `{detail, issues: [{row, column, message}], totalIssues}`. `row=0` означает файл в целом, иначе физическую строку CSV с учётом заголовка. Показываются до 100 ошибок; импорт целиком отклоняется. Ошибки JSON-контракта также возвращают 422 в стандартном формате FastAPI.

Новый успешный ответ содержит `schemaVersion:2`, `methodVersion:flow-history-v2`, полный объект configuration, источник, plan, quality, summary, observations, checkpoints и assumptions. Полный пример: `history.configured.example.json`; правила и формулы: `HISTORY_IMPORT.md`. Архивные отчёты schemaVersion 1 / flow-history-v1 читаются в исходном виде; пример — history.example.json. Формулы и численные результаты с учебными параметрами совпадают с прежними.

Расчёт выполняется вне блокировки текущей симуляции. В блокировке сохраняются исходный CSV и отчёт одной транзакцией. Ключ включает текст CSV после нормализации BOM/CRLF, всю конфигурацию с сортировкой ключей JSON и версию метода; имя файла не входит. Повтор возвращает исходный сохранённый отчёт, включая исходное имя и дату. Семантически одинаковые CSV с другим порядком столбцов или разделителем считаются разными загрузками. Смена версии метода создаёт отдельный отчёт, старый не перезаписывается. Список импортов включает schemaVersion, methodVersion и configuration, когда эти поля есть в сохранённом отчёте; старым записям конфигурация не дописывается.

`source=synthetic_example` выставляется при точном совпадении содержимого с учебным примером после нормализации BOM/CRLF; остальные файлы получают `user_csv`. Это описание происхождения загрузки, не подтверждение данных предприятия. Импорт никогда не переводит оперативный двойник в режим live/historical и не влияет на текущую revision.

## Интерфейс архива (0.5)

Версия интерфейса 0.5 совместима с API 0.4.0. `ArchiveSource` использует только два существующих GET-маршрута runs. Снимок типизирован как `StoredTwinSnapshot` без receivedAt; текущий `TwinSnapshot` по-прежнему требует время получения. Маршруты, формат базы и серверные команды не менялись.

Список содержит до 50 записей `{runId, createdAt, updatedAt, good}` и `currentRunId`. Ответ архива валидируется до отображения: идентификатор должен совпасть с запросом, история должна быть монотонной и не выходить за время/счётчики снимка, времена событий и счётчики работы оборудования не могут выходить за прошедшую часть смены.

Оперативный снимок обновляется независимо от архива. Старая revision текущего сценария отмечается в отчёте; JSON и печать используют показанный снимок без автоматической подмены на более свежий. Подробности — ARCHIVE.md.

## Настройки участка (0.6)

`configure_line` использует тот же транзакционный и идемпотентный протокол команд. Объект configuration строго содержит shiftPlan (целое 1–100000), arrivalIntervalSec (целое 5–3600), stationCyclesSec (ровно пять целых 5–3600), bufferCapacities (ровно четыре целых 1–100). Подробный пример — CONFIGURATION.md.

Новый сценарий сразу содержит рассчитанное состояние на 08:45, паузу и скорость 20×. Нормативы и вместимости хранятся в состоянии каждого runId, поэтому архив сохраняет конфигурацию без миграции схемы. `reset` с 0.6 повторяет параметры текущего сценария. Для возврата к учебным значениям следует явно отправить их через configure_line.

GET twin и ответы на команды добавляют необязательное для старых клиентов поле capabilities со значением `["configure_line", "history_configuration"]`; архивный снимок его не требует. Версии схем снимка (2) и состояния (1) не менялись. history_configuration разрешает в интерфейсе передачу нормативов при импорте CSV; без этого признака остаются чтение отчётов и прежний импорт с учебными параметрами. При явной передаче конфигурации клиент принимает только отчёт v2 с совпадением всех отправленных параметров.
